= Verne — Coexistence des processeurs
:lang: fr
:toc:

== Contrat de la tranche

Verne ne réclame aucune annotation et conserve `false` comme valeur de retour de `process`. Un processeur voisin peut réclamer sa propre annotation et produire des modèles Java pendant la même compilation. La tranche couvre les deux ordres explicites de chargement sur le chemin classique des processeurs, ainsi que la découverte de leurs deux services sur ce chemin.

Une déclaration dont le type est encore absent, ou une navigation dont le type symbolique est encore erroné faute de génération, diffère seulement le gabarit concerné. Aucun diagnostic provisoire ni source Java de ce gabarit n'est émis. Les autres gabarits continuent à être vérifiés. Aux tours non terminaux suivants, Verne reprend les gabarits en attente avec les symboles courants de javac, y compris lorsqu'un modèle dépend d'un second type généré plus tard. Les types doivent devenir disponibles avant le dernier tour ; aucun gabarit n'est généré au tour terminal.

Une erreur certaine, notamment de syntaxe, de visibilité ou de propriété sur un type résolu, reste un refus normal. Si le type demeure absent au dernier tour, le diagnostic en attente est émis une seule fois avec son code Verne, son identifiant logique et sa position. Un paramètre de type absent conserve `VERNE-TYP-003`. L'attente d'un type de navigation non résolu utilise également ce code, à la position de l'interpolation. Les diagnostics différés peuvent apparaître après ceux d'autres ressources ; ils partagent toujours le budget de 64 erreurs détaillées et son marqueur de saturation. Des sources valides peuvent avoir été produites avant un refus différé ; la compilation entière échoue.

L'inventaire, les noms, les liens et les octets des ressources sont contrôlés et lus une seule fois, avec les bornes existantes. Les sources décodées nécessaires à une reprise sont conservées en mémoire pour cette seule compilation ; aucun nouveau flux de fichier n'est ouvert lors des reprises. Chaque tentative possède un nouvel analyseur et ses tables de paramètres ; le budget de lecture et celui des diagnostics ne sont pas réinitialisés entre les tours. Les sources générées ou refusées définitivement ne sont pas reprises et ne doivent pas provoquer de création Java en double.

Les entrées doivent rester stables pendant la compilation. Les listes d'attente et les diagnostics appartiennent à l'instance du processeur et sont vidés au tour terminal ; ils ne sont partagés ni entre tâches ni entre compilations concurrentes. Aucun état statique mutable, chargement réflexif de modèle, dépendance tierce ou contrôle supplémentaire au rendu n'est introduit. La progression des tours dépend de javac et des sources produites par les autres processeurs ; Verne ne crée pas de source artificielle pour provoquer un tour et ne borne pas le comportement d'un processeur tiers défectueux.

Les tests emploient un véritable processeur Java contrôlé qui génère des fichiers sources avec `Filer` et vérifie qu'il reçoit son annotation. Ils ne remplacent pas le compilateur Verne. Les essais avec des bibliothèques de processeurs tierces, leur découverte par modules et leur raccordement conjoint dans une application Maven restent des qualifications distinctes.

== Preuves de vérification

Les dix tests de `CoexistenceProcesseursTest` couvrent la conservation de l'annotation du voisin dans les deux ordres de chargement, un paramètre généré, un modèle produit au deuxième tour, un type de navigation généré pour un record source, deux types générés successivement, un type restant absent, une propriété invalide après apparition du modèle, le budget de 65 diagnostics, deux compilations concurrentes et la découverte automatique des deux services.

Avant correction, sept tests échouaient avec un refus prématuré `VERNE-TYP-003` ou `VERNE-TYP-001`. Les trois témoins de coexistence sans type différé, d'erreur unique et de saturation réussissaient déjà. Après introduction des attentes par gabarit et des reprises aux tours suivants, les dix tests réussissent. Les rendus sont exécutés sur le chemin des modules avec le seul JDK ; Unicode et CRLF sont comparés exactement dans le cas prévu. Une erreur de création Java en double ferait échouer ces constructions réelles.

La vérification complète propre `./mvnw -ntp clean verify` totalise 129 tests sur Mac, sans échec, erreur ni test ignoré. Le générateur de rendu reste identique pour les types déjà résolus ; aucun contrôle d'attente n'est ajouté à l'exécution. Cette tranche ne comporte pas de nouvelle campagne de performances ni de vérification Windows/Linux.
