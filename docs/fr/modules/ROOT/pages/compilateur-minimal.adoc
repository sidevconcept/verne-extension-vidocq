= Verne — Compilateur minimal
:lang: fr
:toc:

État : première implémentation du sous-ensemble texte, au 17 octobre 2026.
La construction et les tests initiaux réussissent ; les fonctionnalités plus larges de l'architecture restent des objectifs.

== Usage livré

Le réacteur construit d'abord `verne-compilation`, puis exécute `verne-verification`. Une dépendance explicite en portée test impose cet ordre, même si Maven parallélise les modules ; elle n'ajoute rien à la portée d'exécution.
Le compilateur est un module Java explicite `io.vidocq.verne.compilation`, dépendant seulement de `java.compiler` et du module de base du JDK.
Il fournit `javax.annotation.processing.Processor` par `module-info.java`.
Le banc vérifie l'appel explicite et la découverte automatique sur les chemins des processeurs classique et modulaire de javac. Une link:application-maven.adoc[application Maven consommatrice] autonome vérifie aussi la configuration du processeur et le lancement du JAR applicatif.

Exécuter depuis la racine, sous Windows :

[source,powershell]
----
.\mvnw.cmd clean verify
----

Sous Unix, dont macOS :

[source,shell]
----
./mvnw clean verify
----

Les applications du banc compilent les gabarits et leurs modèles Java sources dans la même invocation de javac, puis s'exécutent sur le chemin des modules.
Les classes générées dépendent uniquement du JDK ; elles n'exigent aucun JAR Verne à l'exécution.
Un module de cœur distinct n'est donc pas créé sans besoin dans cette tranche.

=== Contrat de découverte du processeur

Le compilateur permet le chargement automatique par javac 25, sans option `-processor` ni annotation applicative. L'application fournit toujours les deux options Verne obligatoires. Le processeur est placé soit sur `-processorpath`, avec son descripteur standard `META-INF/services/javax.annotation.processing.Processor`, soit sur `--processor-module-path`, avec le fournisseur déclaré dans `module-info.java`. En ligne de commande, ces chemins explicites suffisent à activer le traitement avec javac 25 ; `-proc:full` rend aussi ce choix explicite. Les appels à l'API `JavaCompiler.getTask` du banc spécifient `-proc:full` : leur activation implicite n'est pas assimilée à celle de la ligne de commande. Un répertoire de classes complet et une archive JAR contenant ces mêmes classes et ressources offrent le même comportement avec cette activation explicite.
La découverte reste limitée au chemin explicitement fourni au compilateur ; elle n'ajoute aucun balayage métier ni dépendance au rendu. Les entrées de configuration restent des chaînes non nulles fournies par l'outil de construction ; leur absence conserve les diagnostics de configuration existants. Les modèles Java sources sont résolus dans la même invocation et tous les gabarits sont vérifiés, même inutilisés. Un gabarit invalide doit donc faire échouer la construction avec son code et sa position Verne ; un processeur non chargé ne constitue jamais une validation.
Avec `-proc:none`, aucun de ces chemins ne déclenche de génération ni de validation. La seule présence du processeur sur `--class-path`, sans activation du traitement ni chemin de processeurs explicite, ne déclenche pas non plus le traitement sous javac 25. Ces compilations témoins n'utilisent pas les classes de rendu et ne prouvent aucune validité des gabarits.
Le fournisseur public sans argument est instancié par le compilateur ; son état et ses budgets restent propres à chaque compilation. Aucun état statique mutable ni ressource persistante supplémentaire n'est introduit. Les flux de lecture et de génération conservent leur fermeture existante. Les applications générées s'exécutent sur le chemin des modules avec le seul JDK, sans le processeur. Le traitement conjoint et les types produits aux tours suivants sont décrits dans link:coexistence-processeurs.adoc[le contrat de coexistence] ; le raccordement Maven est décrit dans link:application-maven.adoc[son contrat dédié].

== Sources et génération

Le processeur reçoit `verne.racine.gabarits` et `verne.profil.sortie=texte`.
Une racine absente ou un profil différent produit `VERNE-CFG-001`, sans interprétation implicite comme texte brut.
Les fichiers `.verne` sont parcourus dans un ordre déterministe ; les répertoires symboliques ne sont pas suivis.
Une ressource réelle hors de la racine est refusée ; les erreurs de lecture ou de génération sont signalées sans chemin machine.
Les essais de liens symboliques sur plusieurs systèmes restent à compléter.

=== Racine et liens symboliques

La racine déclarée doit résoudre un répertoire existant : une cible existante qui n'est pas un répertoire produit `VERNE-CFG-001` ; une racine introuvable ou impossible à résoudre produit `VERNE-IO-001`.
Un lien symbolique utilisé comme racine est accepté et sa cible réelle définit la frontière autorisée.
Un lien de fichier `.verne` est accepté si sa cible réelle reste sous cette frontière ; son nom logique détermine la classe générée. Une cible externe est refusée avec `VERNE-SEC-001` avant lecture de son contenu.
Un lien de fichier `.verne` cassé ou impossible à résoudre produit `VERNE-IO-001`, avec son identifiant relatif et la position `1:1` ; les autres ressources continuent à être vérifiées et la compilation entière échoue.
Les liens vers des répertoires ne sont pas parcourus, même si leur nom se termine par `.verne` ou qu'ils créent un cycle.
Les diagnostics n'exposent ni chemin absolu de la racine ou de la cible, ni contenu du fichier externe.
Les parcours et flux sont fermés à la fin de leur utilisation ; aucun état ni ressource n'est partagé entre compilations. Les entrées doivent rester stables pendant la compilation ; aucune garantie contre leur remplacement concurrent n'est revendiquée.

=== Nombre de ressources

Une compilation accepte de zéro à 1 024 ressources `.verne`, borne incluse. Cette première borne fixe limite l'inventaire conservé en mémoire ; elle ne constitue ni une mesure de performance ni un budget mémoire global.
Les fichiers ordinaires sélectionnés, liens de fichiers et liens cassés sont comptés ; les répertoires et les liens vers des répertoires ne le sont pas.
À la 1 025e ressource sélectionnée, l'inventaire s'arrête et la compilation produit `VERNE-LIM-002`, sans chemin machine ni contenu source. Aucun gabarit n'est lu, analysé ou généré dans cette invocation.
Dans la borne, le tri et les diagnostics existants sont conservés. Le compteur et la liste appartiennent à l'invocation du processeur ; aucun état partagé ni ressource persistante n'est ajouté et le parcours est fermé, y compris au refus.
Cette borne ne limite pas le nombre de répertoires ou de fichiers non sélectionnés parcourus, le volume total de sources dans la borne, ni les compilations concurrentes. Le budget cumulé de lecture est défini ci-dessous ; les autres budgets restent distincts.

=== Budget cumulé de lecture des sources

Une invocation du processeur accepte au plus 8 mébioctets, soit 8 388 608 octets lus pour les sources `.verne`, borne incluse. Le budget porte sur les octets UTF-8, avant décodage et retrait des commentaires ; il ne borne ni la taille des documents rendus ni toute la mémoire du compilateur Java.
Les ressources sont lues dans l'ordre déterministe de l'inventaire, après les contrôles de cible autorisée et de nom. Chaque lecture consomme le budget, y compris celle d'un fichier ensuite refusé pour encodage, syntaxe ou taille individuelle ; l'octet de sondage de dépassement individuel est compté. Plusieurs noms logiques visant le même fichier sont comptés séparément. Les ressources rejetées avant lecture ne consomment pas ce budget.
La lecture de chaque fichier s'arrête au premier octet au-delà de la plus petite des deux bornes restantes : un mébioctet pour le fichier et le budget cumulé disponible. Au premier dépassement cumulé, `VERNE-LIM-006` désigne la ressource à `1:1`, sans chemin machine ni contenu source. Le traitement s'arrête avant décodage, analyse et génération de ce fichier et des suivants ; les sources déjà générées ne sont pas retirées et la compilation entière échoue. Si les deux bornes sont franchies par le même octet, la limite cumulée est prioritaire ; sinon `VERNE-LIM-001` conserve son rôle pour un dépassement individuel.
Un fichier vide reste accepté lorsque le budget est exactement atteint. Le compteur appartient à l'invocation, sans état partagé entre compilations, y compris concurrentes. Les flux sont fermés avant tout refus ; les entrées doivent rester stables pendant la compilation. Aucun nouveau contrôle n'est ajouté au rendu.

=== Encodage et noms

Les sources sont décodées strictement en UTF-8, sans remplacement des octets invalides.
La limite initiale est un mébioctet, soit 1 048 576 octets par fichier, borne incluse.
La lecture s'arrête au premier octet au-delà de cette borne.
Cette limite concerne les octets sources, et non le nombre de caractères ou la taille du document rendu.

Le nom simple du fichier détermine la classe, en mettant sa première lettre en majuscule : `bonjour.verne` produit `io.vidocq.verne.genere.Bonjour`.
Les répertoires ne participent pas encore au nom de classe : deux ressources de même nom simple sont donc refusées, même dans des sous-répertoires différents.
Le nom doit être un identifiant Java admissible.
Pour détecter les collisions, le nom de classe est normalisé en NFC, converti en minuscules avec `Locale.ROOT`, puis normalisé à nouveau en NFC. Deux noms donnant la même clé sont refusés avec `VERNE-LIA-001`, indépendamment de la langue du poste.
Cette clé ne renomme ni la classe générée ni les données du document. Les équivalences de compatibilité Unicode ne sont pas fusionnées ; cette règle ne prétend pas reproduire tous les systèmes de fichiers.
Le diagnostic porte l'identifiant relatif et la position `1:1` de la seconde ressource dans l'ordre de parcours ; le fichier en collision n'est ni lu ni généré. La compilation entière échoue, même si le programme ne référence aucun de ces gabarits.
La table des noms reste locale à l'invocation du processeur ; aucun état partagé, accès réflexif ou ressource supplémentaire à fermer n'est introduit.
Les autres règles de nommage portable restent à préciser avant généralisation.
Les sources générées ne contiennent ni horodatage, ni chemin absolu.

== Grammaire effectivement acceptée

[cols="2,4",options="header"]
|===
|Forme |Comportement
|Texte hors directive |Conservé exactement, y compris CRLF, LF, tabulations et caractères supplémentaires Unicode
|`{@java.lang.String nom}` |Déclare un paramètre obligatoire `nom` de type chaîne ; ne produit aucun texte
|`{@exemple.Personne personne}` |Déclare un paramètre objet dont le type public et non générique est résolu par le compilateur Java
|`{nom}` |Interpole une chaîne ou une valeur scalaire primitive connue
|`{personne.nom}` |Accède directement au composant `nom` d'un record public ; aucun accès réflexif
|`{personne.adresse.ville}` |Enchaîne les composants de records ; chaque étape est vérifiée statiquement
|`{! commentaire !}` |Retire le commentaire sans supprimer sa ligne
|`\{` |Produit une accolade ouvrante littérale
|`\\` |Produit un antislash littéral
|===

Les espaces entourant le contenu d'une directive sont retirés pour son analyse, pas ceux du document.
Les déclarations sont collectées dans l'ordre source, qui détermine l'ordre des paramètres de la méthode générée.
Elles ont une portée globale dans le gabarit : cette tranche n'a pas de blocs ni de portée locale.
Chaque nom de paramètre doit être un identifiant Java non réservé, sans caractère ignoré par Java.
Les noms métier peuvent être accentués ; la validation complète de leurs formes normalisées reste à réaliser.

Les types génériques, tableaux et déclarations de paramètres primitifs ne font pas encore partie de ce contrat.
Un objet public peut être reçu comme paramètre, mais seules les propriétés correspondant aux composants de records sont accessibles.
Les champs ordinaires, accesseurs de classes ordinaires, méthodes arbitraires et opérations d'introspection ne sont pas exposés.
Un record ne peut pas être interpolé directement par un appel implicite à `toString` ; sa valeur finale doit être une chaîne ou un scalaire primitif.

Les sections, conditions, boucles, opérateurs, remplacements, inclusions et formats autres que texte sont explicitement hors de cette tranche.
Leur syntaxe ne doit pas être rendue silencieusement comme si elle était prise en charge.

== Contrat des classes générées

Chaque classe est finale, sans état et sans constructeur public.
Sa méthode statique `rendre` renvoie une chaîne et reçoit les paramètres dans leur ordre de déclaration.
Les références obligatoires sont contrôlées avant le rendu, et chaque navigation intermédiaire est contrôlée avant l'appel d'accesseur.
Une référence nulle provoque `NullPointerException` avec un message français portant `VERNE-REN-001` ; aucun contenu métier n'est inclus dans ce message.
Une chaîne vide demeure une valeur valide.

La génération utilise un tampon local par appel ; aucun état global ou contexte de requête n'est ajouté.
Les variables générées évitent les collisions avec les noms de paramètres, y compris `java`, `resultat` et le nom de tampon proposé par le générateur.
Les données interpolées ne sont jamais analysées comme des directives.
Le profil texte n'échappe pas les caractères HTML ; il ne doit donc pas être utilisé comme une protection HTML.

Les littéraux Java sont échappés, y compris guillemets, antislashs et caractères de contrôle.
Le texte est fractionné en fragments d'au plus 4 000 unités UTF-16, sans scinder une paire de substituts.
Cette borne évite de dépasser la taille d'une constante de classe Java, même avec des caractères dont l'encodage modifié nécessite plusieurs octets.
Le contrat n'inclut pas encore une sortie en flux, un plafond de caractères rendus ou un rendu asynchrone.

=== Préparation du tampon des grands documents

À partir de 4 000 unités UTF-16 de texte statique rendu, la génération prépare la capacité du tampon à partir du texte et des valeurs interpolées. Les déclarations et commentaires retirés ne participent pas à cette longueur.
Chaque interpolation est évaluée une seule fois, dans l'ordre du gabarit, après le contrôle des paramètres obligatoires. Sa représentation textuelle est conservée dans une variable locale avant l'assemblage ; les primitives gardent la représentation de leur ajout au tampon Java.
Les chaînes vides, les diagnostics de nullité et le découpage des constantes restent inchangés. Les noms locaux évitent ceux de tous les paramètres. Aucun état partagé, dépendance tierce ou second appel d'accesseur n'est introduit.
La somme des longueurs est calculée en `long`, puis saturée à la capacité entière maximale du tampon pour éviter un débordement arithmétique. Ce calcul n'ajoute pas de limite de rendu ; une allocation impossible reste soumise aux erreurs de ressources de la JVM.
Les documents plus petits conservent leur stratégie d'assemblage. Le contrôle d'allocations de vérification utilise `jdk.management` uniquement dans son application de test : sur le JDK 25 de référence, le rendu d'un bloc ASCII de 65 536 caractères suivi d'une valeur Unicode doit allouer moins de sept octets par caractère statique après échauffement. Ce budget ciblé n'est pas une garantie globale de mémoire ni un seuil de temps d'exécution.

=== Nombre de paramètres déclarés

Chaque gabarit accepte de zéro à 255 paramètres obligatoires, borne incluse, dans leur ordre de déclaration. Les types déclarables actuels sont tous des références Java, occupant chacune une unité dans la signature JVM ; 255 est la limite de la méthode statique générée. Cette borne devra être réexaminée avant toute déclaration de primitives ou modification du point d'entrée.
La 256e déclaration syntaxiquement valide d'un nom distinct produit `VERNE-LIM-004` à son accolade ouvrante, avant résolution de son type et avant création de la source Java du fichier. Une déclaration dupliquée conserve `VERNE-TYP-002` ; commentaires et délimiteurs échappés ne déclarent aucun paramètre. Les autres fichiers restent vérifiés.
Le diagnostic n'expose ni contenu source ni chemin machine. Le compteur est la table de paramètres propre au fichier ; aucun état partagé, accès d'exécution ou ressource supplémentaire n'est introduit. Les contrôles de nullité et l'ordre des paramètres acceptés sont conservés. Cette borne ne garantit ni la taille du corps de méthode ni les autres budgets du compilateur.

=== Profondeur des navigations de records

Une interpolation accepte au plus 32 accès de composant de record, borne incluse : le paramètre seul a une profondeur nulle, `personne.nom` une profondeur de un. La limite s'applique séparément à chaque occurrence ; les points des types déclarés, les commentaires et les délimiteurs échappés n'y participent pas.
Après les contrôles de syntaxe et du nombre d'interpolations, une expression de profondeur 33 produit `VERNE-LIM-005` à son accolade ouvrante, avant toute résolution de son paramètre et de ses propriétés. L'analyse du fichier s'arrête sans créer sa source Java ; les autres gabarits restent vérifiés. Le diagnostic ne contient ni expression, ni donnée source, ni chemin machine.
Cette borne fixe limite l'imbrication de l'expression Java générée et le travail de résolution par occurrence ; elle ne garantit ni un budget global de compilation, ni la taille de méthode générée. Dans la borne, le typage statique, l'ordre des accès et les refus de valeurs nulles `VERNE-REN-001` restent identiques. Aucun compteur partagé, nouvelle ressource ou contrôle de profondeur à l'exécution n'est ajouté ; les rendus restent indépendants et sans réflexion.

=== Nombre d'interpolations

Chaque gabarit accepte au plus 1 024 occurrences d'interpolation, borne incluse. Répéter la même expression compte à chaque occurrence ; les déclarations, commentaires et délimiteurs échappés ne comptent pas.
Le compteur appartient à l'analyse du fichier courant et repart de zéro pour chaque gabarit, sans état partagé entre compilations ni modification du rendu dans la borne.
La 1 025e interpolation syntaxiquement admissible provoque `VERNE-LIM-003`, positionné sur son accolade ouvrante selon les règles de ligne et colonne existantes. L'analyse du fichier s'arrête avant résolution des expressions et avant ouverture de sa source générée ; les autres fichiers restent vérifiés.
Le diagnostic ne contient ni donnée du document ni chemin machine ; aucun flux supplémentaire n'est ouvert. Cette première borne limite le nombre d'interpolations conservées, sans garantir la taille de la méthode Java générée ni borner le volume total de texte. Les bornes des déclarations et de profondeur des navigations sont définies séparément ci-dessus.

=== Budget de génération de la méthode de rendu

Chaque gabarit accepte un coût pondéré de génération d'au plus 60 000 unités, borne incluse. Le coût est fixé pour le générateur actuel : 128 unités fixes, 12 par paramètre déclaré, 12 par fragment de texte émis (au plus 4 000 unités UTF-16, sans couper une paire de substituts), 48 par occurrence d'interpolation et 16 par accès de record dans ces occurrences. Les commentaires et déclarations ne produisent aucun fragment ; un commentaire séparant deux textes empêche leur fusion dans le générateur actuel et leurs fragments sont comptés séparément.
Ce budget prudent encadre le cumul d'opérations dans une méthode, au-delà des bornes indépendantes d'interpolations et de profondeur. Il s'agit d'unités conventionnelles, et non d'une mesure exacte des octets de bytecode ou d'une garantie sur toutes les limites de javac et de la JVM. Les pondérations devront être réexaminées avant toute modification de la forme du code généré.
Après analyse syntaxique et déclarations, le dépassement produit `VERNE-LIM-008` à `identifiant.verne:1:1`, avant résolution des expressions et ouverture de la source Java du fichier. Le message ne contient ni expression, ni valeur source, ni chemin machine. Les autres fichiers continuent à être vérifiés dans les budgets existants ; les sources déjà produites ne sont pas retirées et la compilation entière échoue.
Le coût est propre au fichier et calculé sans état partagé ni ressource supplémentaire. Dans la borne, le code généré et les règles de nullité, d'ordre d'évaluation et de concurrence ne changent pas. Aucun compteur ni contrôle supplémentaire n'est ajouté au rendu.

=== Nombre de diagnostics de compilation

Une instance du processeur, pour une compilation, émet au plus 64 erreurs Verne détaillées. Toutes les erreurs issues de la découverte, de la lecture et de l'analyse des gabarits partagent ce budget, y compris les erreurs différées entre tours ; les avertissements et erreurs propres à javac ou à d'autres processeurs n'en font pas partie.
Les 64 premières erreurs conservent leurs codes et positions. Si une 65e erreur Verne est rencontrée, elle est remplacée par un unique diagnostic global `VERNE-LIM-007` signalant la saturation ; aucun identifiant, expression, donnée source ni chemin machine n'est ajouté à ce message. Le nombre maximal de diagnostics Verne est donc 65, marqueur compris. Les ressources suivantes ne sont ni résolues, lues, analysées ni générées. Un fichier valide rencontré après la 64e erreur reste vérifié tant qu'aucune 65e erreur n'est rencontrée.
La compilation échoue dès la première erreur ; les sources déjà générées ne sont pas retirées. Les ressources et flux ouverts sont fermés par les contrôles existants. Le compteur et l'état de saturation appartiennent à l'invocation et ne sont pas partagés entre compilations, y compris concurrentes. Les erreurs d'exécution `VERNE-REN-001` et le code de rendu ne changent pas. Cette borne ne garantit ni un budget mémoire global ni la taille des messages et des méthodes Java générées. Une configuration de javac limitant les erreurs à moins de 65 peut masquer des diagnostics, y compris le marqueur.

La première erreur d'analyse arrête le fichier courant ; le processeur poursuit les autres fichiers tant que les budgets le permettent.
Une erreur empêche la compilation réussie de l'application, même si le gabarit n'est jamais appelé.
Les types encore absents ou symboliquement non résolus peuvent différer le gabarit selon link:coexistence-processeurs.adoc[le contrat de coexistence]. Ils ne produisent aucune erreur provisoire ; les attentes persistantes sont signalées une seule fois au tour terminal. Le remappage des erreurs javac issues du code généré reste à implémenter. Le budget ci-dessus limite les seuls diagnostics Verne.

== Première tranche de portabilité des noms
