= Verne — Compilateur minimal
:lang: fr
:toc:

État : première implémentation du sous-ensemble texte, au 17 octobre 2026.
La construction et les tests initiaux réussissent ; les fonctionnalités plus larges de l'architecture restent des objectifs.

== Usage livré

Le réacteur construit d'abord `verne-compilation`, puis exécute `verne-verification`. Une dépendance explicite en portée test impose cet ordre, même si Maven parallélise les modules ; elle n'ajoute rien à la portée d'exécution.
Le compilateur est un module Java explicite `io.vidocq.verne.compilation`, dépendant seulement de `java.compiler` et du module de base du JDK.
Il fournit `javax.annotation.processing.Processor` par `module-info.java`.
Le banc vérifie l'appel explicite et la découverte automatique sur les chemins des processeurs classique et modulaire de javac. Une link:application-maven.adoc[application Maven consommatrice] autonome vérifie aussi la configuration du processeur et le lancement du JAR applicatif.

Exécuter depuis la racine, sous Windows :

[source,powershell]
----
.\mvnw.cmd clean verify
----

Sous Unix, dont macOS :

[source,shell]
----
./mvnw clean verify
----

Les applications du banc compilent les gabarits et leurs modèles Java sources dans la même invocation de javac, puis s'exécutent sur le chemin des modules.
Les classes générées dépendent uniquement du JDK ; elles n'exigent aucun JAR Verne à l'exécution.
Un module de cœur distinct n'est donc pas créé sans besoin dans cette tranche.

=== Contrat de découverte du processeur

Le compilateur permet le chargement automatique par javac 25, sans option `-processor` ni annotation applicative. L'application fournit toujours les deux options Verne obligatoires. Le processeur est placé soit sur `-processorpath`, avec son descripteur standard `META-INF/services/javax.annotation.processing.Processor`, soit sur `--processor-module-path`, avec le fournisseur déclaré dans `module-info.java`. En ligne de commande, ces chemins explicites suffisent à activer le traitement avec javac 25 ; `-proc:full` rend aussi ce choix explicite. Les appels à l'API `JavaCompiler.getTask` du banc spécifient `-proc:full` : leur activation implicite n'est pas assimilée à celle de la ligne de commande. Un répertoire de classes complet et une archive JAR contenant ces mêmes classes et ressources offrent le même comportement avec cette activation explicite.
La découverte reste limitée au chemin explicitement fourni au compilateur ; elle n'ajoute aucun balayage métier ni dépendance au rendu. Les entrées de configuration restent des chaînes non nulles fournies par l'outil de construction ; leur absence conserve les diagnostics de configuration existants. Les modèles Java sources sont résolus dans la même invocation et tous les gabarits sont vérifiés, même inutilisés. Un gabarit invalide doit donc faire échouer la construction avec son code et sa position Verne ; un processeur non chargé ne constitue jamais une validation.
Avec `-proc:none`, aucun de ces chemins ne déclenche de génération ni de validation. La seule présence du processeur sur `--class-path`, sans activation du traitement ni chemin de processeurs explicite, ne déclenche pas non plus le traitement sous javac 25. Ces compilations témoins n'utilisent pas les classes de rendu et ne prouvent aucune validité des gabarits.
Le fournisseur public sans argument est instancié par le compilateur ; son état et ses budgets restent propres à chaque compilation. Aucun état statique mutable ni ressource persistante supplémentaire n'est introduit. Les flux de lecture et de génération conservent leur fermeture existante. Les applications générées s'exécutent sur le chemin des modules avec le seul JDK, sans le processeur. Le traitement conjoint et les types produits aux tours suivants sont décrits dans link:coexistence-processeurs.adoc[le contrat de coexistence] ; le raccordement Maven est décrit dans link:application-maven.adoc[son contrat dédié].

== Sources et génération

Le processeur reçoit trois options obligatoires : `verne.racine.gabarits`, `verne.paquet` et `verne.profil.sortie`, dont la valeur est `texte`, `html`, `xml` ou `json`.
Une racine absente, un paquet absent ou invalide, ou un profil absent ou inconnu produit `VERNE-CFG-001`, sans interprétation implicite comme texte brut ni paquet par défaut. Ce profil est celui des gabarits sans suffixe de profil ; un gabarit peut choisir le sien par son nom, comme décrit dans link:#_profils_de_sortie_html_xml_et_json[les profils de sortie].
Les fichiers `.verne` sont parcourus dans un ordre déterministe ; les répertoires symboliques ne sont pas suivis.
Une ressource réelle hors de la racine est refusée ; les erreurs de lecture ou de génération sont signalées sans chemin machine.
Le processeur déclare la dernière version source prise en charge par le compilateur Java qui l'exécute ; Java 25 reste la version minimale du projet.

=== Paquet des classes générées

`verne.paquet` désigne le paquet Java qui reçoit toutes les classes générées de l'invocation, par exemple `-Averne.paquet=exemple.gabarits`.
La valeur est un nom qualifié Java : chaque segment est un identifiant non réservé, sans caractère ignoré par Java ; une valeur vide, un segment vide ou un mot réservé produit `VERNE-CFG-001` sans lecture des gabarits.
Le paquet appartient à l'application : dans un module nommé, il fait partie du module compilé et n'est exporté que si son descripteur le demande.
Deux modules chargés ensemble doivent déclarer des paquets distincts, car la plateforme de modules refuse un même paquet dans deux modules d'une même couche ; Verne n'impose plus de paquet commun.
Les sous-répertoires de la racine ne participent pas encore au paquet. Verne ne vérifie pas qu'une classe applicative du même nom existe déjà dans ce paquet ; une création impossible relève de `VERNE-IO-001` ou du diagnostic de javac.
Les essais de liens symboliques sur plusieurs systèmes restent à compléter.

=== Racine et liens symboliques

La racine déclarée doit résoudre un répertoire existant : une cible existante qui n'est pas un répertoire produit `VERNE-CFG-001` ; une racine introuvable ou impossible à résoudre produit `VERNE-IO-001`.
Un lien symbolique utilisé comme racine est accepté et sa cible réelle définit la frontière autorisée.
Un lien de fichier `.verne` est accepté si sa cible réelle reste sous cette frontière ; son nom logique détermine la classe générée. Une cible externe est refusée avec `VERNE-SEC-001` avant lecture de son contenu.
Un lien de fichier `.verne` cassé ou impossible à résoudre produit `VERNE-IO-001`, avec son identifiant relatif et la position `1:1` ; les autres ressources continuent à être vérifiées et la compilation entière échoue.
Les liens vers des répertoires ne sont pas parcourus, même si leur nom se termine par `.verne` ou qu'ils créent un cycle.
Les diagnostics n'exposent ni chemin absolu de la racine ou de la cible, ni contenu du fichier externe.
Une erreur pendant le parcours de la racine, par exemple un sous-répertoire illisible, produit un unique `VERNE-IO-001` sans chemin machine ; l'inventaire est alors abandonné et aucun gabarit de l'invocation n'est lu ni généré. Le processeur ne laisse jamais une exception de parcours interrompre javac.
Les parcours et flux sont fermés à la fin de leur utilisation ; aucun état ni ressource n'est partagé entre compilations. Les entrées doivent rester stables pendant la compilation ; aucune garantie contre leur remplacement concurrent n'est revendiquée.

=== Nombre de ressources

Une compilation accepte de zéro à 1 024 ressources `.verne`, borne incluse. Cette première borne fixe limite l'inventaire conservé en mémoire ; elle ne constitue ni une mesure de performance ni un budget mémoire global.
Les fichiers ordinaires sélectionnés, liens de fichiers et liens cassés sont comptés ; les répertoires et les liens vers des répertoires ne le sont pas.
À la 1 025e ressource sélectionnée, l'inventaire s'arrête et la compilation produit `VERNE-LIM-002`, sans chemin machine ni contenu source. Aucun gabarit n'est lu, analysé ou généré dans cette invocation.
Dans la borne, le tri et les diagnostics existants sont conservés. Le compteur et la liste appartiennent à l'invocation du processeur ; aucun état partagé ni ressource persistante n'est ajouté et le parcours est fermé, y compris au refus.
Cette borne ne limite pas le nombre de répertoires ou de fichiers non sélectionnés parcourus, le volume total de sources dans la borne, ni les compilations concurrentes. Le budget cumulé de lecture est défini ci-dessous ; les autres budgets restent distincts.

=== Budget cumulé de lecture des sources

Une invocation du processeur accepte au plus 8 mébioctets, soit 8 388 608 octets lus pour les sources `.verne`, borne incluse. Le budget porte sur les octets UTF-8, avant décodage et retrait des commentaires ; il ne borne ni la taille des documents rendus ni toute la mémoire du compilateur Java.
Les ressources sont lues dans l'ordre déterministe de l'inventaire, après les contrôles de cible autorisée et de nom. Chaque lecture consomme le budget, y compris celle d'un fichier ensuite refusé pour encodage, syntaxe ou taille individuelle ; l'octet de sondage de dépassement individuel est compté. Plusieurs noms logiques visant le même fichier sont comptés séparément. Les ressources rejetées avant lecture ne consomment pas ce budget.
La lecture de chaque fichier s'arrête au premier octet au-delà de la plus petite des deux bornes restantes : un mébioctet pour le fichier et le budget cumulé disponible. Au premier dépassement cumulé, `VERNE-LIM-006` désigne la ressource à `1:1`, sans chemin machine ni contenu source. Le traitement s'arrête avant décodage, analyse et génération de ce fichier et des suivants ; les sources déjà générées ne sont pas retirées et la compilation entière échoue. Si les deux bornes sont franchies par le même octet, la limite cumulée est prioritaire ; sinon `VERNE-LIM-001` conserve son rôle pour un dépassement individuel.
Un fichier vide reste accepté lorsque le budget est exactement atteint. Le compteur appartient à l'invocation, sans état partagé entre compilations, y compris concurrentes. Les flux sont fermés avant tout refus ; les entrées doivent rester stables pendant la compilation. Aucun nouveau contrôle n'est ajouté au rendu.

=== Encodage et noms

Les sources sont décodées strictement en UTF-8, sans remplacement des octets invalides.
La limite initiale est un mébioctet, soit 1 048 576 octets par fichier, borne incluse.
La lecture s'arrête au premier octet au-delà de cette borne.
Cette limite concerne les octets sources, et non le nombre de caractères ou la taille du document rendu.

Le nom simple du fichier, normalisé en NFC et privé de son éventuel suffixe de profil, détermine la classe, en mettant sa première lettre en majuscule : avec `-Averne.paquet=exemple.gabarits`, `bonjour.verne` et `bonjour.html.verne` produisent `exemple.gabarits.Bonjour`.
Le suffixe de profil est le dernier segment avant `.verne`, séparé par un point : `texte`, `html`, `xml` ou `json`, en minuscules. Tout autre suffixe, comme `yaml` ou `HTML`, produit `VERNE-LIA-001` à `identifiant.verne:1:1`, sans lecture du fichier ; les autres ressources continuent à être vérifiées. Deux fichiers qui ne diffèrent que par leur suffixe produisent la même classe et sont refusés comme collision.
Un même nom écrit en NFC ou en NFD, selon le système de fichiers ou l'outil qui l'a créé, produit donc la même classe, utilisable depuis des sources Java écrites en NFC.
Les répertoires ne participent pas encore au nom de classe : deux ressources de même nom simple sont donc refusées, même dans des sous-répertoires différents.
Le nom doit être un identifiant Java admissible.
Pour détecter les collisions, le nom de classe est normalisé en NFC, converti en minuscules avec `Locale.ROOT`, puis normalisé à nouveau en NFC. Deux noms donnant la même clé sont refusés avec `VERNE-LIA-001`, indépendamment de la langue du poste.
Cette clé ne modifie ni la casse de la classe générée ni les données du document. Les équivalences de compatibilité Unicode ne sont pas fusionnées ; cette règle ne prétend pas reproduire tous les systèmes de fichiers.
Le diagnostic porte l'identifiant relatif et la position `1:1` de la seconde ressource dans l'ordre de parcours ; le fichier en collision n'est ni lu ni généré. La compilation entière échoue, même si le programme ne référence aucun de ces gabarits.
La table des noms reste locale à l'invocation du processeur ; aucun état partagé, accès réflexif ou ressource supplémentaire à fermer n'est introduit.
Les autres règles de nommage portable restent à préciser avant généralisation.
Les sources générées ne contiennent ni horodatage, ni chemin absolu.
Une création ou une écriture de source Java impossible, par exemple un type déjà produit par un autre processeur, produit `VERNE-IO-001` à `identifiant.verne:1:1` ; les ressources suivantes continuent à être vérifiées et la compilation échoue.

== Grammaire effectivement acceptée

[cols="2,4",options="header"]
|===
|Forme |Comportement
|Texte hors directive |Conservé exactement, y compris CRLF, LF, tabulations et caractères supplémentaires Unicode
|`{@java.lang.String nom}` |Déclare un paramètre obligatoire `nom` de type chaîne ; ne produit aucun texte
|`{@exemple.Personne personne}` |Déclare un paramètre objet dont le type public et non générique est résolu par le compilateur Java
|`{nom}` |Interpole une chaîne ou une valeur scalaire primitive connue
|`{personne.nom}` |Accède directement au composant `nom` d'un record public ; aucun accès réflexif
|`{personne.adresse.ville}` |Enchaîne les composants de records ; chaque étape est vérifiée statiquement
|`{! commentaire !}` |Retire le commentaire sans supprimer sa ligne
|`\{` |Produit une accolade ouvrante littérale
|`\\` |Produit un antislash littéral
|===

Les espaces entourant le contenu d'une directive sont retirés pour son analyse, pas ceux du document.
Les fins de ligne du fichier sont rendues telles quelles : un dépôt Git qui normalise les fins de ligne peut donc changer le document selon le poste. Déclarer `*.verne -text`, ou une fin de ligne fixe, dans le `.gitattributes` de l'application rend le rendu indépendant de l'extraction.
Les déclarations sont collectées dans l'ordre source, qui détermine l'ordre des paramètres de la méthode générée.
Elles ont une portée globale dans le gabarit : cette tranche n'a pas de blocs ni de portée locale.
Chaque nom de paramètre doit être un identifiant Java non réservé, sans caractère ignoré par Java.
Les noms métier peuvent être accentués ; la validation complète de leurs formes normalisées reste à réaliser.

Les types génériques, tableaux et déclarations de paramètres primitifs ne font pas encore partie de ce contrat.
Un objet public peut être reçu comme paramètre, mais seules les propriétés correspondant aux composants de records sont accessibles.
Les champs ordinaires, accesseurs de classes ordinaires, méthodes arbitraires et opérations d'introspection ne sont pas exposés.
Un record ne peut pas être interpolé directement par un appel implicite à `toString` ; sa valeur finale doit être une chaîne ou un scalaire primitif.
Les annotations de type, par exemple `@Nullable String` sur un composant de record, ne changent pas cette classification : la valeur reste une chaîne et son contrôle de nullité au rendu est conservé.

=== Visibilité entre modules

Lorsque l'application est un module nommé, chaque type déclaré et chaque record traversé par une navigation doit être accessible depuis le paquet généré : il appartient au module compilé, ou à un module que celui-ci lit et qui exporte son paquet, sans restriction ou vers ce module.
La lecture comprend `java.base`, les modules requis par le descripteur et, de proche en proche, leurs dépendances `requires transitive`. Un type déclaré dans un paquet non exporté, exporté seulement vers d'autres modules ou appartenant à un module non lu produit `VERNE-TYP-003` à la position de la déclaration. Une navigation vers un record inaccessible produit `VERNE-TYP-001` à la position de l'interpolation, comme pour un record non public. Ces refus interviennent avant création de la source Java, au lieu d'une erreur javac dans le code généré.
Dans le module sans nom, seuls les paquets exportés sans restriction des modules nommés sont accessibles ; les types du chemin des classes le restent. Cette vérification utilise uniquement le modèle symbolique de javac.

Les sections, conditions, boucles, opérateurs, remplacements, inclusions et formats autres que texte sont explicitement hors de cette tranche.
Leur syntaxe ne doit pas être rendue silencieusement comme si elle était prise en charge.

== Contrat des classes générées

Chaque classe est finale, sans état et sans constructeur public.
Sa méthode statique `rendre` renvoie une chaîne et reçoit les paramètres dans leur ordre de déclaration.
Les références obligatoires sont contrôlées avant le rendu, et chaque navigation intermédiaire est contrôlée avant l'appel d'accesseur.
Une référence nulle provoque `NullPointerException` avec un message français portant `VERNE-REN-001` ; aucun contenu métier n'est inclus dans ce message.
Une chaîne vide demeure une valeur valide.

La génération utilise un tampon local par appel ou, pour les grands documents, un assemblage unique ; aucun état global ou contexte de requête n'est ajouté.
Les variables générées évitent les collisions avec les noms de paramètres, y compris `java`, `resultat` et le nom de tampon proposé par le générateur.
Les données interpolées ne sont jamais analysées comme des directives.
Le profil texte n'échappe pas les caractères HTML ; il ne doit donc pas être utilisé comme une protection HTML. Les profils `html` et `xml` sont décrits ci-dessous.

Les littéraux Java sont échappés, y compris guillemets, antislashs et caractères de contrôle.
Le texte est fractionné en fragments d'au plus 4 000 unités UTF-16, sans scinder une paire de substituts.
Cette borne évite de dépasser la taille d'une constante de classe Java, même avec des caractères dont l'encodage modifié nécessite plusieurs octets.
Le contrat n'inclut pas encore une sortie en flux, un plafond de caractères rendus ou un rendu asynchrone.

=== Profils de sortie HTML, XML et JSON

Chaque gabarit a un profil : celui de son suffixe, comme `page.html.verne`, `flux.xml.verne`, `donnees.json.verne` ou `note.texte.verne`, sinon le profil par défaut de `-Averne.profil.sortie`. Une même invocation peut donc produire du texte, du HTML, du XML et du JSON. Un suffixe choisit explicitement un profil ; l'absence de suffixe ne désactive aucune protection, puisqu'elle applique le profil configuré. Le contenu déclaré fiable reste à livrer : dans les profils HTML, XML et JSON, toute chaîne interpolée est échappée, sans exception.

==== Échappement des valeurs

[cols="1,1,1,2",options="header"]
|===
|Caractère |HTML |XML |Remarque
|`&` |`&amp;` |`&amp;` |
|`<` |`&lt;` |`&lt;` |
|`>` |`&gt;` |`&gt;` |Couvre aussi la séquence `]]>` en XML
|`"` |`&quot;` |`&quot;` |
|`'` |`&#39;` |`&apos;` |
|CR |inchangé |`&#13;` |Conservé malgré la normalisation des fins de ligne XML
|LF, tabulation |inchangés |`&#10;`, `&#9;` dans une valeur d'attribut |Conservés malgré la normalisation des valeurs d'attribut XML
|===

L'échappement s'applique aux chaînes et au type `char`. Les autres primitives (`boolean`, `byte`, `short`, `int`, `long`, `float`, `double`) ne peuvent contenir aucun de ces caractères et sont rendues sans transformation. La valeur d'origine n'est jamais modifiée ; une valeur déjà échappée l'est une seconde fois, car Verne ne distingue pas encore un contenu fiable.
Une valeur sans caractère à échapper n'est pas recopiée avant d'entrer dans le document : les petits documents l'écrivent directement dans leur tampon, les grands l'utilisent telle quelle. L'échappement est une méthode privée de chaque classe générée : aucune bibliothèque n'est requise à l'exécution, aucun état n'est partagé et le rendu reste sûr en concurrence.

En XML, une valeur contenant un caractère interdit par XML 1.0 provoque `IllegalArgumentException` avec `VERNE-REN-002`, sans la valeur dans le message. Sont interdits les contrôles de U+0000 à U+001F autres que tabulation, LF et CR, U+FFFE, U+FFFF et les substituts isolés. Aucun texte n'est alors renvoyé. Le texte d'un gabarit XML est soumis à la même règle à la compilation : un caractère interdit dans le fichier source produit `VERNE-SYN-004` à sa position.

==== Contextes d'interpolation

À la compilation, Verne suit le balisage du texte statique pour connaître le contexte de chaque interpolation. Les directives Verne, commentaires et déclarations, ne participent pas au balisage ; un délimiteur échappé `\{` y compte comme une accolade.
Une interpolation n'est acceptée que dans deux contextes :

* le texte d'un élément ;
* une valeur d'attribut entre guillemets doubles ou simples.

Tout autre contexte produit `VERNE-SEC-002` à la position de l'interpolation, avant création de la source Java, avec le nom du contexte et sans valeur : nom de balise ouvrante ou fermante, nom d'attribut, emplacement entre les attributs, valeur d'attribut sans guillemets, commentaire, déclaration (`<!DOCTYPE`, déclaration d'entité), section `CDATA` et instruction de traitement.

Le profil HTML refuse en plus :

* le contenu des éléments `script`, `style`, `xmp`, `iframe`, `noembed`, `noframes`, `noscript` et `plaintext`, dont le texte n'est pas décodé par le navigateur ;
* les attributs d'événement, dont le nom commence par `on`, et les attributs `style` et `srcdoc` ;
* les attributs portant une URL : `href`, `src`, `action`, `formaction`, `srcset`, `imagesrcset`, `xlink:href`, `data`, `poster`, `background`, `cite`, `longdesc`, `lowsrc`, `dynsrc`, `usemap`, `codebase`, `classid`, `archive`, `profile`, `manifest`, `ping`, `icon`, `itemtype` et `itemid` ;
* la valeur de `http-equiv`, et celle de `content` dans un élément `meta` qui porte aussi `http-equiv`.

Les noms de balise et d'attribut sont comparés sans tenir compte de la casse en HTML. Le contenu de `textarea` et `title` est du texte échappé : une interpolation y est acceptée, sauf au milieu d'une balise fermante en cours d'écriture. Un chevron `<` suivi d'un caractère qui n'ouvre pas de balise reste du texte, comme dans un navigateur.

Une URL dynamique exige une validation de schéma que ce profil ne fournit pas encore : elle est refusée plutôt que simplement échappée. Le profil XML ne connaît pas la sémantique des vocabulaires XHTML, SVG ou autres ; il ne détecte ni URL ni script dans un attribut et ne doit pas remplacer le profil HTML pour une page web.

==== Profil JSON

Le profil JSON suit les littéraux de chaîne du texte statique, entre guillemets doubles non échappés, pour placer chaque interpolation :

* dans un littéral de chaîne, toute valeur interpolable est acceptée. Les chaînes et les `char` y sont échappés, les autres primitives y sont écrites telles quelles, par exemple `"id-{n}"` ;
* hors d'un littéral, seules les primitives numériques et booléennes sont acceptées, écrites telles quelles. Une chaîne ou un `char` hors d'un littéral produit `VERNE-SEC-002` : il faut l'entourer de guillemets dans le gabarit, Verne n'en ajoute pas implicitement ;
* juste après un antislash statique d'un littéral, au milieu d'une séquence d'échappement, une interpolation produit `VERNE-SEC-002`.

[cols="1,1",options="header"]
|===
|Caractère d'une chaîne |Écrit
|`"` |`\"`
|`\` |`\\`
|retour arrière, saut de page, LF, CR, tabulation |`\b`, `\f`, `\n`, `\r`, `\t`
|autre contrôle de U+0000 à U+001F |`\u00xx`, en hexadécimal minuscule
|U+2028, U+2029 |`\u2028`, `\u2029`, pour rester sûr dans un script
|substitut isolé |`\uxxxx`, pour que le document reste encodable en UTF-8
|===

Les autres caractères, dont `/`, les lettres accentuées et les emoji, sont écrits tels quels. Une valeur sans caractère à échapper n'est pas recopiée avant d'entrer dans le document.
Hors d'un littéral, un `double` ou un `float` infini ou `NaN` provoque `IllegalArgumentException` avec `VERNE-REN-003`, sans la valeur dans le message ; aucun texte n'est renvoyé. Dans un littéral de chaîne, `NaN` et `Infinity` restent du texte valide.
Verne ne vérifie pas la structure JSON du texte statique : accolades, crochets, virgules et noms de membres sont la responsabilité du gabarit. Une accolade ouvrante littérale s'écrit `\{`, la fermante telle quelle. Les directives Verne, commentaires et déclarations, ne participent pas au suivi des littéraux.

==== Limites

L'échappement ne garantit pas la validité structurelle du document : un gabarit peut produire un balisage mal formé, et Verne ne vérifie pas qu'un gabarit se termine hors d'une balise, car un fragment est admis. Une référence de caractère formée par le texte statique et une valeur, comme `&` suivi de `lt;`, reste un caractère de texte et ne peut pas créer de balise.
Le coût pondéré de génération est inchangé ; l'appel d'échappement ajoute quelques octets par interpolation à la méthode de rendu, dans la marge du budget.

=== Assemblage unique des grands documents

À partir de 4 000 unités UTF-16 de texte statique rendu, la classe générée n'utilise plus de tampon. Les déclarations et commentaires retirés ne participent pas à cette longueur.
Chaque interpolation est évaluée une seule fois, dans l'ordre du gabarit, après le contrôle des paramètres obligatoires. Sa représentation textuelle est conservée dans une variable locale ; les primitives gardent la représentation Java de `String.valueOf`.
Le document est ensuite assemblé en une seule opération à partir des fragments statiques et de ces représentations, dans l'ordre du gabarit. La longueur et l'encodage interne de la chaîne finale sont déterminés avant la copie : le texte est copié une seule fois, y compris lorsqu'une valeur hors Latin-1 suit un long texte Latin-1. Cet assemblage utilise uniquement le JDK.
Les chaînes vides, les diagnostics de nullité, le découpage des constantes et le budget pondéré de génération restent inchangés. Les noms locaux évitent ceux de tous les paramètres. Aucun état partagé, dépendance tierce ou second appel d'accesseur n'est introduit ; chaque appel n'utilise que ses variables locales et reste sûr en concurrence.
Ce mode n'ajoute pas de limite de rendu : un document dont la longueur dépasse la capacité d'une chaîne Java provoque l'erreur de ressources levée par la JVM.
Sous le seuil, un tampon dimensionné est utilisé, comme décrit ci-dessous ; l'assemblage unique y ralentirait le rendu.
Les contrôles d'allocations de vérification utilisent `jdk.management` uniquement dans leur application de test. Sur le JDK 25 de référence, après échauffement, le rendu d'un bloc ASCII de 65 536 caractères doit allouer, par caractère statique, moins de 1,5 octet lorsqu'il est suivi d'une valeur Latin-1, moins de 2,5 octets lorsqu'il est suivi d'une valeur hors Latin-1, et moins de sept octets dans le contrôle historique. Ces budgets ciblés ne sont ni une garantie globale de mémoire ni un seuil de temps d'exécution.

=== Tampon dimensionné des petits documents

Sous 4 000 unités UTF-16 de texte statique, chaque interpolation est aussi évaluée une seule fois, dans l'ordre du gabarit, après le contrôle des paramètres obligatoires, et conservée dans une variable locale. Le tampon local est ensuite alloué une seule fois, avec une capacité égale à la longueur du texte statique, plus la longueur de chaque chaîne interpolée avant échappement, plus 24 par primitive, ce qui couvre la représentation la plus longue d'un `long` ou d'un `double`. La somme est calculée en `long` puis saturée à la capacité entière maximale ; un document trop grand reste soumis aux erreurs de ressources de la JVM.
Avec les profils HTML et XML, chaque valeur est échappée directement dans ce tampon, par plages de caractères, sans chaîne intermédiaire. Un document dont l'échappement dépasse la capacité prévue agrandit le tampon, sans autre effet. En XML, un caractère interdit lève `VERNE-REN-002` pendant l'écriture : le tampon local est abandonné et aucun texte n'est renvoyé.
L'ordre d'évaluation, les contrôles de nullité, l'échappement et le texte produit sont inchangés ; seules la forme des sources générées et les allocations changent. Aucun état partagé n'est introduit et le rendu reste sûr en concurrence.
Sur le JDK 25 de référence, après échauffement, le rendu d'une fiche d'environ 700 caractères Latin-1 doit allouer moins de 2,5 octets par caractère du document en profil texte. En profil HTML, avec environ 10 % de caractères à échapper dans les valeurs, il doit allouer moins de 4,5 octets par caractère du document produit.

=== Nombre de paramètres déclarés

Chaque gabarit accepte de zéro à 255 paramètres obligatoires, borne incluse, dans leur ordre de déclaration. Les types déclarables actuels sont tous des références Java, occupant chacune une unité dans la signature JVM ; 255 est la limite de la méthode statique générée. Cette borne devra être réexaminée avant toute déclaration de primitives ou modification du point d'entrée.
La 256e déclaration syntaxiquement valide d'un nom distinct produit `VERNE-LIM-004` à son accolade ouvrante, avant résolution de son type et avant création de la source Java du fichier. Une déclaration dupliquée conserve `VERNE-TYP-002` ; commentaires et délimiteurs échappés ne déclarent aucun paramètre. Les autres fichiers restent vérifiés.
Le diagnostic n'expose ni contenu source ni chemin machine. Le compteur est la table de paramètres propre au fichier ; aucun état partagé, accès d'exécution ou ressource supplémentaire n'est introduit. Les contrôles de nullité et l'ordre des paramètres acceptés sont conservés. Cette borne ne garantit ni la taille du corps de méthode ni les autres budgets du compilateur.

=== Profondeur des navigations de records

Une interpolation accepte au plus 32 accès de composant de record, borne incluse : le paramètre seul a une profondeur nulle, `personne.nom` une profondeur de un. La limite s'applique séparément à chaque occurrence ; les points des types déclarés, les commentaires et les délimiteurs échappés n'y participent pas.
Après les contrôles de syntaxe et du nombre d'interpolations, une expression de profondeur 33 produit `VERNE-LIM-005` à son accolade ouvrante, avant toute résolution de son paramètre et de ses propriétés. L'analyse du fichier s'arrête sans créer sa source Java ; les autres gabarits restent vérifiés. Le diagnostic ne contient ni expression, ni donnée source, ni chemin machine.
Cette borne fixe limite l'imbrication de l'expression Java générée et le travail de résolution par occurrence ; elle ne garantit ni un budget global de compilation, ni la taille de méthode générée. Dans la borne, le typage statique, l'ordre des accès et les refus de valeurs nulles `VERNE-REN-001` restent identiques. Aucun compteur partagé, nouvelle ressource ou contrôle de profondeur à l'exécution n'est ajouté ; les rendus restent indépendants et sans réflexion.

=== Nombre d'interpolations

Chaque gabarit accepte au plus 1 024 occurrences d'interpolation, borne incluse. Répéter la même expression compte à chaque occurrence ; les déclarations, commentaires et délimiteurs échappés ne comptent pas.
Le compteur appartient à l'analyse du fichier courant et repart de zéro pour chaque gabarit, sans état partagé entre compilations ni modification du rendu dans la borne.
La 1 025e interpolation syntaxiquement admissible provoque `VERNE-LIM-003`, positionné sur son accolade ouvrante selon les règles de ligne et colonne existantes. L'analyse du fichier s'arrête avant résolution des expressions et avant ouverture de sa source générée ; les autres fichiers restent vérifiés.
Le diagnostic ne contient ni donnée du document ni chemin machine ; aucun flux supplémentaire n'est ouvert. Cette première borne limite le nombre d'interpolations conservées, sans garantir la taille de la méthode Java générée ni borner le volume total de texte. Les bornes des déclarations et de profondeur des navigations sont définies séparément ci-dessus.

=== Budget de génération de la méthode de rendu

Chaque gabarit accepte un coût pondéré de génération d'au plus 60 000 unités, borne incluse. Le coût est fixé pour le générateur actuel : 128 unités fixes, 12 par paramètre déclaré, 12 par fragment de texte émis (au plus 4 000 unités UTF-16, sans couper une paire de substituts), 48 par occurrence d'interpolation et 16 par accès de record dans ces occurrences. Les commentaires et déclarations ne produisent aucun fragment ; un commentaire séparant deux textes empêche leur fusion dans le générateur actuel et leurs fragments sont comptés séparément.
Ce budget prudent encadre le cumul d'opérations dans une méthode, au-delà des bornes indépendantes d'interpolations et de profondeur. Il s'agit d'unités conventionnelles, et non d'une mesure exacte des octets de bytecode ou d'une garantie sur toutes les limites de javac et de la JVM. Les pondérations devront être réexaminées avant toute modification de la forme du code généré.
Après analyse syntaxique et déclarations, le dépassement produit `VERNE-LIM-008` à `identifiant.verne:1:1`, avant résolution des expressions et ouverture de la source Java du fichier. Le message ne contient ni expression, ni valeur source, ni chemin machine. Les autres fichiers continuent à être vérifiés dans les budgets existants ; les sources déjà produites ne sont pas retirées et la compilation entière échoue.
Le coût est propre au fichier et calculé sans état partagé ni ressource supplémentaire. Dans la borne, le code généré et les règles de nullité, d'ordre d'évaluation et de concurrence ne changent pas. Aucun compteur ni contrôle supplémentaire n'est ajouté au rendu.

=== Nombre de diagnostics de compilation

Une instance du processeur, pour une compilation, émet au plus 64 erreurs Verne détaillées. Toutes les erreurs issues de la découverte, de la lecture et de l'analyse des gabarits partagent ce budget, y compris les erreurs différées entre tours ; les avertissements et erreurs propres à javac ou à d'autres processeurs n'en font pas partie.
Les 64 premières erreurs conservent leurs codes et positions. Si une 65e erreur Verne est rencontrée, elle est remplacée par un unique diagnostic global `VERNE-LIM-007` signalant la saturation ; aucun identifiant, expression, donnée source ni chemin machine n'est ajouté à ce message. Le nombre maximal de diagnostics Verne est donc 65, marqueur compris. Les ressources suivantes ne sont ni résolues, lues, analysées ni générées. Un fichier valide rencontré après la 64e erreur reste vérifié tant qu'aucune 65e erreur n'est rencontrée.
La compilation échoue dès la première erreur ; les sources déjà générées ne sont pas retirées. Les ressources et flux ouverts sont fermés par les contrôles existants. Le compteur et l'état de saturation appartiennent à l'invocation et ne sont pas partagés entre compilations, y compris concurrentes. Les erreurs d'exécution `VERNE-REN-001` et le code de rendu ne changent pas. Cette borne ne garantit ni un budget mémoire global ni la taille des messages et des méthodes Java générées. Une configuration de javac limitant les erreurs à moins de 65 peut masquer des diagnostics, y compris le marqueur.

== Diagnostics rattachés aux fichiers de gabarit (proposé)

Cette section est une proposition de VERNE-002 (ticket nº 27), soumise à D-002.
Elle ne décrit aucune capacité livrée et ne modifie les contrats précédents qu'après décision explicite et réalisation de VERNE-004.

=== Observations et portée

Sur la base `6c6825883176d237e4ece2f8115e91506af357b1`, `signalerErreur` transmet un message sans élément à `Messager`.
Avec javac 25.0.1, un collecteur de diagnostics retourne une source nulle et les positions `-1`, même si le texte contient `bonjour.verne:2:1`.
Maven 3.9.16 avec maven-compiler-plugin 3.14.1 affiche ce texte sans position structurée ; son résumé peut le répéter.
Ces répétitions de présentation ne sont pas des émissions supplémentaires de Verne.

L'API standard https://docs.oracle.com/en/java/javase/25/docs/api/java.compiler/javax/annotation/processing/Messager.html[Messager] accepte un élément Java, une annotation ou sa valeur comme indication de position, mais aucun fichier arbitraire avec ligne et colonne.
Un élément Java d'origine pointerait le modèle Java, pas le gabarit ; il n'existe pas nécessairement pour un gabarit textuel.
Le préfixe proposé ci-dessous reste donc du texte : aucun lien cliquable, marqueur dans le panneau des problèmes ou soulignement du gabarit n'est garanti par le processeur seul.
Un tel rattachement structuré demanderait une intégration propre à l'outil, à délimiter avant réalisation ; aucune API interne de javac ni dépendance d'exécution n'est proposée.
Le remappage du Java généré (T-DIA-02) reste hors périmètre.

=== Format et choix de chemin soumis à D-002

Recommandation conditionnelle soumise à D-002 : conserver par défaut le format livré et l'interdiction des chemins absolus.
Aucun clic dans un IDE n'a été observé lors de cette étude. Le bénéfice de navigation du préfixe absolu reste une hypothèse à qualifier, pas une contrepartie démontrée à l'exposition du chemin machine.
Une option proposée `verne.diagnostics.chemins`, absente ou égale à `relatifs`, conserve exactement :

[source,text]
----
VERNE-SYN-001 : bonjour.verne:2:1 : interpolation ou déclaration non fermée.
----

La valeur explicite `absolus` active un affichage destiné au poste de développement :

[source,text]
----
/projet/src/main/verne/bonjour.verne:2:1 : VERNE-SYN-001 : interpolation ou déclaration non fermée.
----

Le chemin affiché est celui du fichier sélectionné par l'inventaire sous la racine effective obtenue par `Path.of(racineDeclaree).toRealPath()`, comme dans le processeur actuel.
Une racine relative est résolue par le système de fichiers Java contre le répertoire de travail du processus compilateur ; ce répertoire n'est pas présumé être celui du projet Maven ou de l'IDE.
Ne pas appliquer `normalize()` à la racine déclarée avant `toRealPath()` : avec un lien symbolique suivi de `..`, la simplification lexicale peut changer le répertoire désigné.
Le chemin affiché correspond à la racine effective absolue, suivie du chemin relatif conservé par l'inventaire ; il n'est pas reconstruit depuis le nom de classe.
La cible d'un lien utilisé comme racine est donc visible dans ce mode, tandis que le nom d'un lien de fichier admissible reste celui de l'inventaire : ne pas remplacer ce dernier par sa cible réelle dans le message.
Le contrôle existant de la cible réelle du fichier reste préalable à la lecture ; un lien refusé vers l'extérieur ne reçoit jamais ce préfixe absolu ni un extrait.
Par exemple, si `/essai/liens/lien` vise `/essai/cible/enfant`, la racine déclarée `/essai/liens/lien/../gabarits` désigne `/essai/cible/gabarits`, pas `/essai/liens/gabarits`. Le préfixe utilise donc `/essai/cible/gabarits/bonjour.verne`.
Ces règles supposent toujours les entrées stables pendant la compilation ; elles ne garantissent pas qu'un fichier reste inchangé jusqu'à un clic ultérieur.
Ce mode expose volontairement le chemin de la racine dans les journaux : il constitue une exception explicite à l'interdiction actuelle, à accepter par D-002.
L'éligibilité au chemin absolu et à l'extrait dépend d'une position réelle dans une source autorisée et décodée, pas de la famille du code.
La liste suivante est fermée pour cette proposition ; tout code nouveau exige une décision de contrat avant de devenir éligible.
L'éligibilité permet l'affichage enrichi seulement lorsque l'option correspondante est activée ; elle ne modifie ni gravité ni budget.

[cols="2,1,4",options="header"]
|===
|Codes |Éligibles |Position et justification
|`VERNE-SYN-001`, `VERNE-SYN-002`, `VERNE-SYN-004` |Oui |Position originale du délimiteur, de l'échappement ou du caractère XML interdit ; source autorisée et décodée
|`VERNE-TYP-001`, `VERNE-TYP-002`, `VERNE-TYP-003`, `VERNE-TYP-004` |Oui |Déclaration ou interpolation fautive ; inclut le refus de type inconnu encore présent au tour terminal
|`VERNE-SEC-002` |Oui |Refus de contexte HTML, XML ou JSON à sa position source ; ne se confond pas avec le refus de fichier externe
|`VERNE-LIM-003`, `VERNE-LIM-004`, `VERNE-LIM-005` |Oui |Interpolation, déclaration ou navigation qui franchit la limite ; position réelle conservée
|`VERNE-IO-001`, `VERNE-LIA-001`, `VERNE-SEC-001`, `VERNE-SYN-003`, `VERNE-LIM-001`, `VERNE-LIM-006` |Non |Position conventionnelle `1:1` ou diagnostic global ; ni préfixe absolu ni extrait, même lorsqu'un tampon source est disponible
|`VERNE-LIM-008` |Non |Le dépassement du budget global du gabarit utilise l'offset 0 (`1:1`) par convention ; il n'attribue pas la faute au premier caractère
|`VERNE-CFG-001`, `VERNE-LIM-002`, `VERNE-LIM-007` |Non |Diagnostics globaux, sans position inventée
|`VERNE-TYP-005` |Non |Avertissement global sur les gabarits en attente, format existant inchangé
|`VERNE-REN-001`, `VERNE-REN-002`, `VERNE-REN-003` |Non |Erreurs de rendu, hors du diagnostic de compilation étudié
|===

Un diagnostic éligible réellement situé au premier caractère peut lui aussi avoir la position `1:1` : les seuls nombres ne suffisent donc pas à déterminer son éligibilité.
Pour `VERNE-TYP-003` différé, conserver la position et le tampon d'origine du gabarit jusqu'à son émission terminale ; aucune erreur provisoire, nouvelle lecture ni substitution du contenu d'un tour ultérieur n'est permise.
La même table gouverne les deux options ; les diagnostics exclus conservent leur format relatif ou global, sans contenu source.
Les chemins Windows utilisent leurs séparateurs natifs ; les espaces sont conservés, sans guillemets ajoutés.
Pour éviter les lignes de console forgées, un chemin contenant un caractère de contrôle ou de format Unicode est rendu avec chaque caractère concerné remplacé par `\u{HEX}` (hexadécimal majuscule sans zéro initial superflu) et n'est pas promis cliquable.
Les antislashs du chemin restent des séparateurs ; le texte échappé n'est jamais une donnée à réinterpréter ou à ouvrir automatiquement.
Les limites des détecteurs de liens pour espaces, deux-points, Unicode et chemins Windows doivent être qualifiées séparément.

Les valeurs inconnues ou vides d'une option produisent `VERNE-CFG-001` sans réafficher la valeur reçue, avant lecture des gabarits.
Les options absentes utilisent les valeurs par défaut ; aucune valeur Java nulle n'est traitée comme un texte à afficher.
Les diagnostics globaux restent `CODE : message français`, sans position inventée.
Les diagnostics ayant déjà une position conventionnelle `1:1` la conservent ; elle n'indique pas une faute de syntaxe précise.
Les avertissements conservent leur gravité et leur format existants ; les erreurs de rendu restent inchangées.

=== Position et extrait facultatif

Les lignes et colonnes commencent à un. LF, CR et CRLF terminent une ligne ; CRLF n'en compte qu'une.
La colonne compte les points de code Unicode du texte original décodé, avant retrait des commentaires, sans normalisation Unicode : une tabulation compte pour un, un emoji supplémentaire pour un, une lettre suivie d'un accent combinant pour deux.
La position reste celle de l'émetteur existant : délimiteur ouvrant, début d'échappement ou caractère XML interdit selon le diagnostic. La colonne n'est ni un nombre d'unités UTF-16 ni un nombre de graphèmes ou de cellules de terminal.
Pour `tabulation + 🚀 + e + accent combinant + {inconnu`, l'accolade est à la colonne 5, tandis que son indice UTF-16, augmenté de un, vaut 6.
Un adaptateur d'éditeur doit convertir la position selon sa propre convention à partir de la même source ; transmettre directement la colonne en points de code peut décaler la sélection.
T-DIA-01 conserve ainsi sa convention actuelle. Aucune longueur de soulignement n'est inventée.

Une seconde option proposée, `verne.diagnostics.extrait`, absente ou égale à `false`, conserve l'absence de contenu source.
La valeur `true` ajoute deux lignes dans le même message, uniquement pour les codes éligibles de la table ci-dessus :

[source,text]
----
VERNE-SYN-001 : bonjour.verne:2:1 : interpolation ou déclaration non fermée.
  source : {inconnu
  repère : ^
----

L'extrait provient exclusivement du tampon déjà décodé du gabarit, jamais d'une nouvelle lecture, d'une valeur de modèle, d'un fichier externe refusé ou d'une exception brute.
Il expose néanmoins le texte statique de cette ligne, qui peut être confidentiel : D-002 doit aussi accepter cette exception aux clauses actuelles excluant la donnée source.
L'activation est indépendante du mode de chemin ; `false` demeure recommandé pour les journaux partagés.

La fenêtre contient au plus 120 points de code de la ligne source, sans sa fin de ligne.
Pour une position d'indice zéro `p` dans une ligne de longueur `n`, son début est `max(0, p - 40)` et sa fin exclusive `min(n, début + 120)` ; une position de fin de ligne peut placer le repère après le dernier caractère.
Ajouter `...` à chaque côté tronqué.
Dans cette fenêtre, conserver les caractères ASCII imprimables sauf l'antislash, doublé ; représenter tout autre point de code par `\u{HEX}`.
Cette représentation volontairement ASCII évite les séquences de contrôle, les tabulations variables et les ambiguïtés de largeur des emoji et des accents.
Elle diminue aussi la lisibilité du français : `Bonjour Léa {nom` devient `Bonjour L\u{E9}a {nom`.
Ce compromis est conservé dans la proposition pour rendre le repère calculable sans table de largeur propre au terminal ni traitement distinct des caractères composés et décomposés.
L'extrait reste une aide de localisation facultative, et non une reproduction typographique de la source ; une variante Unicode plus lisible demanderait sa propre convention d'alignement et sa qualification.
Le repère est un unique `^`, précédé d'autant d'espaces que la longueur du préfixe affiché avant la position, y compris l'éventuel `...` ; les préfixes `  source : ` et `  repère : ` ont la même largeur.
Exemple pour la ligne Unicode ci-dessus :

[source,text]
----
  source : \u{9}\u{1F680}e\u{301}{inconnu
  repère :                       ^
----

La colonne annoncée reste 5 : la longueur de la représentation échappée n'est pas une nouvelle colonne source.
Le texte d'erreur reste français, avec code stable ; les préfixes propres à javac ou Maven ne sont pas maîtrisés par Verne.

=== Budgets, ressources et vérification attendue

Chaque erreur, préfixe et éventuel extrait compris, correspond à un seul appel à `Messager` et consomme une seule unité du budget existant.
Après 64 erreurs détaillées, la 65e reste le seul `VERNE-LIM-007`, global, sans fichier ni extrait ; ne pas préparer d'extrait pour une erreur supprimée par saturation.
Conserver l'ordre déterministe, l'arrêt du fichier fautif, le traitement différé des types et l'arrêt des ressources suivant la saturation.
Aucune écriture de rapport, nouvelle lecture de fichier, connexion, réflexion métier ou ressource persistante n'est ajoutée.
Le formatage utilise l'état de l'invocation, sans compteur ni tampon statique partagé ; les compilations concurrentes restent isolées.
Les sources doivent rester stables pendant la compilation ; aucune garantie supplémentaire contre leur remplacement concurrent n'est apportée.
L'extrait borné limite sa propre taille, pas celle des chemins ou du message complet ; aucune promesse de performance mesurée n'en découle.

Avant implémentation, VERNE-004 devra écrire et observer en échec les contrôles du nouveau format : valeurs par défaut inchangées, options invalides, LF/CR/CRLF, commentaires multilignes, emoji, accents combinants, tabulations, fenêtre tronquée, antislash et contrôles Unicode, refus de lien externe, erreur sans source, tours différés, saturation à 64/65 erreurs et isolation concurrente.
Il faudra ensuite vérifier leur réussite et la suite complète, sans compter une erreur d'outillage comme phase rouge.
Les essais IDE devront distinguer console, navigation après clic et marqueur de problème, en vérifiant le fichier et la position réellement ouverts.
Les versions et réglages du compilateur, de l'IDE et de ses extensions devront accompagner chaque résultat ; une observation javac ne vaut pas qualification d'Eclipse JDT.
