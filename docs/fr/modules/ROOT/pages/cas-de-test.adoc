= Verne — Cas de test avant implémentation
:lang: fr
:toc:

État : plan de tests. Une première tranche exécutable est décrite dans link:premiers-tests.adoc[son rapport] ; les premiers contrats métier sont validés par la suite décrite dans link:compilateur-minimal.adoc[le rapport actuel], sans valider toutes les familles du plan.
Chaque ligne devient un ou plusieurs tests écrits avant le code correspondant.
Une famille n'est validée qu'après l'exécution de tous ses jeux de données et la revue de ses limites.

== Méthode et oracles

. Définir le contrat et l'oracle attendu sans appeler le moteur pour fabriquer le résultat de référence.
. Écrire le test ; observer son échec pour la bonne raison, puis conserver la trace dans la revue de réalisation.
. Implémenter le comportement minimal ; exécuter les tests concernés et leurs dépendants.
. Améliorer la structure, puis relancer les vérifications pertinentes.
. Relier le test à son identifiant fonctionnel et mettre à jour la documentation.

Les sorties textuelles sont comparées exactement, y compris espaces, fins de ligne et points de code.
Les erreurs sont vérifiées par code, phase et position ; le message français est contrôlé sans figer toute sa ponctuation.
Un test de compilation négative vérifie l'échec du processus, le diagnostic visé et l'absence de livrable exploitable.
Un oracle JSON ou XML utilise un lecteur indépendant uniquement dans les tests ; il ne devient pas une dépendance du moteur.
La couverture de lignes ne démontre pas l'exhaustivité ; combiner tests de branches, jeux générés, tests de mutation ciblés et essais d'intégration.

Les exemples de syntaxe reprennent la notation proposée dans link:architecture.adoc[architecture].
Avant les tests d'expressions avancées, la grammaire et les règles numériques doivent devenir des contrats explicites.
Un cas encore dépendant d'un arbitrage doit être marqué bloqué par ce contrat, jamais interprété librement par l'implémentation.

== Jeux générés et limites de l'exhaustivité

Pour l'analyseur, produire des gabarits à profondeur bornée, puis supprimer ou déplacer chaque token et tronquer les sources.
Pour les chaînes, croiser caractères spéciaux, points de code supplémentaires, longues séquences répétées et frontières de tampon.
Pour la composition, produire des graphes acycliques et des graphes avec cycle injecté ; vérifier ordre des dépendances et diagnostic.
Pour la concurrence, utiliser barrières et complétions pilotées plutôt que des temporisations arbitraires ; répéter avec graines enregistrées.
Les essais d'épuisement mémoire et de blocage s'exécutent dans un processus jetable avec plafond et délai externes.

Ces techniques cherchent des cas non anticipés ; elles ne permettent pas d'affirmer que tous les programmes possibles ont été testés.
Tout défaut découvert enrichit le corpus par un test de non-régression minimal avant sa correction.

== Rapport exigé pour chaque réalisation

Le rapport associe révision, JDK, commande exacte, nombre de tests exécutés, échecs et exclusions motivées.
Il sépare test unitaire, compilation de projet, intégration, sécurité, concurrence et mesure de performances.
La validation avant livraison comporte les systèmes Windows et Linux, une construction propre et une construction incrémentale.
Aucune commande ou résultat fictif ne remplace une exécution : les commandes seront fixées avec les modules réellement créés.
